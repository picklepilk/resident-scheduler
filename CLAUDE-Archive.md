Hard circadian + GR-gap checks run in `validateAll` regardless of `appSettings.enforceRest` (that toggle gates only the pairwise rest-hours check). Rolling 80h/wk pro-rated cap → generator reason `'hoursCapped'`. (superseded 2026-09-27: day→eve allowed)

Soft: `traumaSecondInRun`/`traumaMidRun`/`nightDurationAlternation` (alternation exempt at 12h-window boundaries via `alternationExemptDates`).

- **Night consolidation (2026-10-28, chief explicitly wants it; supersedes the "61% of real runs are 1-3" calibration above)**: `nightShapePenalty` now charges EVERY run beyond a resident's first (edge runs included) via `nightFragmentationCost` (`scheduleQuality.js`; `NIGHT_EXTRA_RUN_AVOIDABLE` 6 / `NIGHT_EXTRA_RUN_FORCED` 2 / `NIGHT_SINGLETON_COST` 6 for interior singles; edge runs stay exempt from the SINGLETON charge only). New `nightMergePass` (`ResidentScheduler.jsx`, runs before and after LNS, deterministic, 40 full-score evals per pass): swaps ownership of a resident's short run (<=3 nights) with a peer's nights on the dates growing another of the resident's runs; adopted only on strict `betterQuality`; replay = `replayNightMerge`. LNS also has a night-focus band (`LNS_NIGHT_FOCUS`) centred on gaps between a resident's runs. Real Block 6 baseline before: C fresh generate 27 isolated singles / 33 multi-run residents (chief hand schedule 6 / 13). Hit rate of the swap is low (rest/streak/rotation eligibility reject most pairs) -- the metric + fill-time terms do most of the work.

### Generator (full originals)
- `generateSchedule()`: coverage-driven, three passes via `fillDayPass` — `'min'` for everything except TRAUMA-D, then TRAUMA-D alone (PGY-1 trauma-day is deliberately the final min step — don't collapse), then `'optional'` top-up (empty pool silently skipped, max is a cap). Candidate pool recomputed fresh per slot — a cached pool once caused double-booking; the decision path must never go through a cache. Never overwrites non-empty cells (`keptCells` — covers manual entries and partial-regenerate identically).
- **Fresh MRV**: greedy re-pick of most-constrained remaining slot after every placement. Counts maintained incrementally (exact ONLY because every `candidatePool` filter reads per-resident state — a new cross-resident filter silently degrades the ordering); the cache is a SORT KEY ONLY; the count is composition-aware (effective sub-pool for FLEX/POD seniority) — that's where the measured win is, don't drop to raw pool size. Ties resolve to earliest original slot (determinism preserved).
- `generateScheduleBest()`: 20 seeded attempts (`baseSeed + i*0x9E3779B9`, `mulberry32` rng injected into `score()`'s tie-break), picked by `betterQuality` — **lexicographic** `(validateAll errors, export-blocking warnings, quality vector)`, never a weighted scalar. Any result replayable: `generateSchedule({...args, rng: mulberry32(report.seed)})`. Solver `FEASIBLE` results are NOT replayable — the returned schedule is the record.
- **Repair pass** (`repair:true`, run once on the winning seed, kept only on strict improvement): Phase 1 same-day/cross-day swaps for unfilled mins, Phase 2 rest-compromise swaps, Phase 3 senior swaps, Phase 4 bounded depth-2 ejection chains. Every move transactional (candidatePool re-check, coverage-min floor, exact revert) and narrowed by `narrowForSeniority`/`podStillSatisfied` (without them repair manufactured hard errors). Pool budget 300 (P1–3) + 200 (P4) — deliberately not shared (P1 exhausts any shared budget). Post-repair report arrays rebuilt from the final schedule, scoped to generated cells only; the quality scorer reads the WHOLE schedule including kept cells.
- **`SCORE_WEIGHTS`/`SCORE_TIERS`** (exported; `scoreWeights.test.js`): every weight classified STRUCTURAL or PREFERENCE; test is a RATCHET (bands can't grow past ceilings, every weight must be classified). Known-inert inversion: preference bands can exceed a shift's deficit worth, but `candidatePool`'s `allAtTarget` filter enforces target fairness upstream — if that filter is ever loosened, revisit (documented A/B rejected a rescale).
- Work-shape scoring: fragmentation charged only beyond `ceil(worked/6)` runs (6-day cap REQUIRES ≥3 runs at target 18); joins the existing last vector slot at 0.5 — never a 5th slot.
- **Area spread** (`SCORE_WEIGHTS.areaShare` 15 STRUCTURAL, DAY/EVE ONLY + `areaSpread` metric): `mixShare` only buckets day/eve/night, so POD-E/MT-E/FLEX-E are one indistinguishable "eve" and area concentration went unscored (measured: residents eligible for all 5 areas finishing an 18-shift block 100% in one area). `areaCount` is maintained at the SAME four sites as `nightAreaCount` (seed, `fillDayPass` commit, repair assign/unassign). **Nights are exempt** — they already have `nightAreaDiversity`, pinned at weight 2 so area spread can never compete with `nightCluster`(40); including nights tripped `chiefBenchmark`'s isolated-single-night-run guard (25 vs 23 ceiling). Weight 15 (not the concentration-optimal 25) because 25 still fails that guard at 24. **The `areaContinuity > 0` gate is load-bearing** — ungated, the term opposes `workShapePenalty`'s within-run area-churn charge and regresses it, the way the reverted Phase 2.3 type-churn term did; gated, it speaks only when a NEW run starts, so continuity governs WITHIN a run and areaShare ACROSS runs. `areaSpread` (excess over `AREA_CONCENTRATION_FLOOR` 0.5) joins the existing last vector slot at 2 — never a 5th slot. A finer per-shift-id twin was built and A/B rejected (inert on 2 of 3 fixtures; the fill-time half regressed restCompromises).
- **AY carryover** (`computeAyPriorTotals`): spreads blended with prior AY totals from PUBLISHED snapshots only, capped at 6 blocks. Strict no-op on empty history; a resident with no history is EXCLUDED from the AY population, never zeroed (zero = maximally under-worked = hammers the newest resident).
- Override capture: hand-edits to a generated schedule logged into `block.overrideLog` via `updateBlockTracked` ONLY (the single mutation choke point). Two guards: previous schedule must have a `generationReport`, and a generation itself (report identity change) is skipped. Cap 500. Report-only — nothing reads it back into generation.
- Readiness gate (`checkGenerateReadiness`): warns (with Generate Anyway) on empty relevant special-day lists + JC presenter gaps (`jcPresentersFor` shared with the planner card).
- **Under-target issues carry `rule: 'underTarget'`** — classify by that id everywhere, never by `message.startsWith('Under target')` (the message text gets suffixes appended — see conference tolerance below — and a prefix classifier is one text edit from silently breaking). `GenerationReportCard`'s per-resident line also reports WHY, via a diagnostic computed at the tail of `generateSchedule` (right after the repair pass): for every under-target resident it counts `openSlots` (dates+shifts where headroom existed and the resident was rotation-eligible) and a `blockedBy` histogram of the hard rule (`allRestBlocked`, `streakBlocked`, `nightCapped`, `halfTargetMet`, …) that rejected them from each one — reusing `candidatePool`'s own reason vocabulary via a separate `UNDER_TARGET_BLOCK_LABELS` display map (unlabelled reasons fall through to the raw id, never blank). This is diagnosis only — nothing reads it back into generation — and it's cheap: it runs after the schedule is frozen so `candidatePool`'s per-resident caches are warm. `generateScheduleBest` passes `deferUnderTargetDiagnostics:true`, which parks the scan on the report as a closure instead of running it, then invokes it once on the winning attempt and **deletes the property** — so the cost is paid on 1 of the 21 internal `generateSchedule` calls, not all 21. The delete is load-bearing: the report is persisted onto the block, a function property would vanish in the JSON round-trip, and a report still carrying one has un-filled `openSlots`/`blockedBy`. Standalone callers omit the flag and get the numbers computed inline.
- **Conference under-target tolerance**: a resident finishing exactly 1 shift short on a block that overlaps an ACEP/AAEM/SAEM window (`getConferencesInBlock`) downgrades that one `underTarget` issue from `error` to `warn` (stops blocking export) and stamps `conferenceTolerated: true` — the TARGET itself is untouched, only export severity relaxes, because inside a 12-hour 'replace' window POD/MT/FLEX 9h shifts become 12h ones that still credit +1 toward target but burn 12h of the 80h rolling cap instead of 9h, so `hoursCapped` binds sooner for everyone working that week. `conferenceTolerated` issues are deliberately absent from `EXPORT_BLOCKING_RULE_IDS` (so the export gate truly stops blocking) but ARE folded into `scoreGenerationResult`'s `blockingWarnCount` (so `betterQuality`'s lexicographic slot 1 still strictly prefers an attempt that reaches full target over one that settles for 1-short) — two callers reading the same issue list for two different questions, same idiom as `twelveHourAllows`'s per-caller `undefined` handling. Don't let a downgrade-to-warn also fall out of the scoring count, or the generator loses all incentive to hit target on conference blocks.
- Progress overlay: `startGenProgress`/`stopGenProgress` in a `finally`; `yieldToPaint()` (double rAF) awaited before every synchronous generator call so the stage label paints. z-100.

### UI conventions (full originals)
- **Dark mode**: override stylesheet in `index.css` (`.dark` sheet), NOT Tailwind `dark:` variants (thousands of class strings). Wrapped in `@media screen` so print/PDF stays light. Exempt on purpose: solid `-500/600/700` button backgrounds with `text-white`, vivid rings/outlines, modal scrims, `SidebarNav`/`DAY_MARKERS.dark` (sidebar is solid dark-navy in every theme). Auth/requests surfaces render inside AppGate's `.dark` wrapper and need the same treatment.
- **`DAY_MARKERS`**: single style table for GR/JC/WW/OFF/VAC/J + pending-R badge across all seven render sites. `onShift` variant is solid `bg-white` + colored ring + `-700` text — **never an alpha tint** (chip background bleeds through). New/changed marker = edit this table, never inline classes.
- **Schedule grid**: sticky header/footer/name-column only work because the scroll container is `overflow-auto` with a bounded `maxHeight` — don't remove the height bound. Z-ladder: cells 10 → header/footer 20 → corner cells 30 (INLINE `zIndex` — `.grid-sticky` is unlayered CSS and beats `@layer utilities` classes) → app header 50 → fullscreen 60 → progress overlay 100 → toast 200. Fullscreen is an in-app `fixed inset-0` overlay, not `requestFullscreen()`.
- **Grid readability**: zoom 50–150% applied as CSS `zoom`, **never `transform: scale`** (breaks every sticky axis); the `maxHeight` calc divides the zoom back out. All three input paths (buttons/wheel/pinch) share ONE clamp inside `setGridZoom`. Column width: `CELL_W = CELL_W_BASE + gridColExtra` local to `ScheduleGrid`. Both persist in `res_ui_prefs` (`normalizeUiPrefs`; `clampGridZoom` typeof-checks, no `Number()` coercion — `Number(true)` is 1). Two-tier header: week band height set on the band ROW (border-box), second tier sticks at `top: WEEK_BAND_H`; bands are MONDAY-started (blocks start Monday; Sunday-start splits the weekend). Weekend cells `bg-slate-100`; `border-l-2` marks Mondays.
- **Cell locking**: `block.lockedCells` inside the block (rides existing persistence); undo pairs `{schedule, lockedCells}`; generator knows nothing about locks (`runPartialRegenerate` clears only unlocked, `keptCells` protects the rest); every bulk lock action = ONE functional `updateBlockTracked` (looping per-cell floods undo); chip `draggable` disabled while lock-paint is on.
- `computeCoverageByDate` is shared by grid footer, Dashboard tiles, Calendar view — never fork it; it reads only `r.id` (works on stub snapshot rosters). `cellViolations` shared by picker + drag-drop (both sides validated against `scheduleClearing`-adjusted state; violations open `DragConfirmModal`). Root `issues`/`issueCounts` memo = ONE `validateAll` pass for all consumers.
- Dashboard is the landing tab (Home tab GONE — read old "Home tab" references as Dashboard). Hosts `BlockCalendarSection` (AY timeline of snapshots + coverage heatmaps), Current Block editor, `AYConferenceEditor`, JC/Holiday date editors, `JournalClubPlanner` (writes `jcPresentDates` via functional `setEmRoster` by id), Special Days, stat cards, `JeopardySickCallsCard`.
- **What's New**: `CHANGELOG` newest-first; change `id` only for interruption-worthy releases; `res_whats_new_seen` device-local; `markChangelogSeen()` is the single writer; `WhatsNewTab` freezes its unseen set at mount so New pills survive the visit that clears them; `renderChangelogText` shared (bold-only markup, deliberate).
- `TimeOffModal` paint math is pure in `src/lib/dateSetPaint.js`; deliberately NOT wired into `ResidentForm` (nested-modal unverified). Requests tab is the only tab component outside the big file; it re-checks its own session/role.
- Coverage tab math lives in `src/lib/coverageComposition.js`; reproduces `computeCoverageByDate`'s two guards (skip `SHIFT_DOW`-inactive, resolve `twelveHourStateFor` once per date).
- **Schedule-tab row grouping** (Category/PGY/Rotation, second `SubTabs` above the category filter pills): pure partition logic in `lib/scheduleGrouping.js`'s `groupResidents(residents, mode, {categories, blockTypes, isEm})` — lib-legal only because `CATEGORIES`/`BLOCK_TYPES_EM`/`isEmResident` are passed as PARAMETERS, never imported (lib/* may never import `ResidentScheduler.jsx`). Always returns `[{cat, members}]`, same shape the category-only version always returned — `cat` is a synthesized `{id,label,badge,rowBg}` descriptor in PGY/rotation mode, which is why `ScheduleGrid`'s banner render and `ResidentCardsView` needed no edits to gain the other two modes. Runs on `visibleResidents` (after the category pills + hide-unscheduled), so filtering and grouping compose. `PGY_OTHER`/`ROT_OTHER` catch-all buckets exist so a garbage `pgy` or an EM resident with an unrecognized `blockType` still renders a row instead of vanishing — same posture as the hide-unscheduled toggle.

- **Prior rest rule (SUPERSEDED 2026-10-15)**: rest between shifts was measured from the LATER of a
  shift's own end or Grand Rounds' own end (12:00), when this resident's GR fell on the day the
  earlier shift ended and that shift ended before GR did (`effectiveShiftEndMs`, `lib/acgmeHours.js`;
  mirrored solver-side in `rest.py`'s `_effective_earlier_end_min` via `payload.gr_end_h`/
  `resident.gr_dates`). Chief decision 2026-10-15 removed this entirely — "the only shifts that count
  towards time off before/after a shift ... are the actual clinical shifts" — rest is now always
  measured strictly from the earlier shift's own end, full stop, in both engines. `effectiveShiftEndMs`
  was deleted outright (every call site just uses `lib/shifts.js`'s plain `shiftEndMs` now).
- **Prior Grand Rounds hour contribution (SUPERSEDED 2026-10-15)**: GR counted a flat 4h
  (`GR_DURATION_H`, 08:00-12:00) toward the weekly-hour caps on every GR weekday, regardless of what
  was worked the day before. Chief decision 2026-10-15: the window now depends on the calendar day
  immediately before GR — 2h (10:00-12:00) after an eve-type shift, 2h (08:00-10:00) after a
  night-type shift ending that morning, 4h (08:00-12:00) otherwise. New `grWindowFor(resident, grDs,
  prevShiftId)` in `lib/acgmeHours.js`; `grHoursOn` grew a 4th `prevShiftId` param (every caller
  threads the shift assigned the day before, looked up across the tail/block boundary where needed).
- **Prior 6-consecutive-work-day streak (SUPERSEDED 2026-10-15)**: a day counted toward the streak if
  a shift was assigned, OR it was the resident's own GR weekday, OR it was a Journal Club presenting
  date (`resident.jcPresentDates`) — unless vacation/approved-off — with a post-overnight-GR exemption
  (a resident who worked a night shift the calendar day immediately before their own GR weekday was
  exempted, since they'd sleep through it; this was also how a BAMC resident could legitimately miss
  one Thursday GR per rotation coming straight off nights). This whole mechanism — `obligationKind`
  (JS), the `obligations`/`obligationsExemptAfterNight`/`priorTailObligations` payload fields, and
  their solver-side consumption in `workday_limits.py`'s `_obligation_term` — existed because a
  shift-less GR Wednesday that didn't count as a workday once let a resident get scheduled 8 days
  straight (one real obligation run silently split into two "legal" <=6 runs by the gap). Chief
  decision 2026-10-15 reversed this ruling outright: the streak now counts CLINICAL SHIFTS ONLY.
  `isStreakWorkDay` collapsed to `!!(rs[ds] || prevRs[ds])`; `obligationKind` was deleted; the three
  payload fields are no longer populated (still accepted/defaulted by `payload.py` for back-compat,
  but `workday_limits.py` needed no code change at all — an empty `obligations` map already made its
  mechanism a pure no-op). Known downstream effect: this measurably loosens `candidatePool`'s hard
  `sixDayRunRestBlocked`/run-length filter around every GR/JC date, which shifted several generator
  exact-number regression tests (`chiefBenchmark.test.js`, `nightContiguity.test.js`,
  `podPgy2Substitute.test.js`, the `conferenceBlock` quality baseline) — reported, not "fixed" by
  adjusting their thresholds, since those are empirical observations of generator behavior, not
  independent correctness checks.

## Archived 2026-10-16: verbose originals of tightened CLAUDE.md bullets (resident-scheduler)

### Persistence / cloud sync (original wording)
- Cloud sync (`// ─── SUPABASE SYNC ───`): hand-rolled PostgREST `sbFetch` (15s timeout), no supabase-js for the transport (it IS used, via `getAccessToken()`, just to fetch the current session token). `SUPABASE_ENABLED` from `%VITE_*%` token injection; `isUnresolvedToken` = unconfigured. One `res_state` row `id:'main'`, whole doc as jsonb.
- **`res_state` RLS is admin-only** (2026-10-14, `migrate_res_state_admin_only.sql` — see that file's DEPLOY ORDER note: client ships before migration runs, else admins lock themselves out). `sbFetch`'s `Authorization` header is the caller's session JWT (`getAccessToken()`, bounded to 5s via `getAccessTokenBounded()` — a hung token refresh must not block a request indefinitely, and must NOT silently fall back to the anon key while `AUTH_ENABLED`; that would masquerade as the exact empty-result ambiguity `sbIsAdmin()` exists to resolve), anon key only as fallback when there's genuinely no session (resolved, not timed out) or `AUTH_ENABLED` is false — **never** send the anon key as `Authorization` for this table again; that was the confirmed data-exposure gap this fix closed (every resident's name + full schedule readable by anyone holding the public anon key). Residents read a narrow, non-schedule slice (block dates, roster names) via the SECURITY DEFINER RPC `public.resident_block_lookup()`, called from `src/residentRequests/blockLookup.js` — never `res_state` directly.
- **Versioning + audit history, NOT last-write-wins** (2026-10-14, `migrate_res_state_history.sql` — DEPLOY ORDER is the OPPOSITE of `migrate_res_state_admin_only.sql`: this migration runs FIRST, client second, because it's purely additive — an old client's plain upsert still works unchanged against it, while a new client's `?version=eq.N` PATCH would 400 against an unmigrated DB). `res_state.version`/`updated_by`/`updated_at` are set ENTIRELY by two triggers (`res_state_set_audit_fields` BEFORE INSERT OR UPDATE, forcing these three regardless of what the client sends; `res_state_archive_history` AFTER UPDATE, archiving OLD into `res_state_history` attributed to OLD's own writer) — never client-supplied, same posture as `profiles`' role-change triggers. `res_state_history`: admin-select-only via `is_admin()`, no insert/update/delete policy for anyone — only the SECURITY DEFINER trigger writes; retention keeps the newest 200 per `row_id`, pruned every write.
- **Every save path is race-safe, including the "unconditional overwrite" ones**: `sbSaveStateVersioned` (`saveCloudNow`'s steady-state path) PATCHes `?version=eq.N` for the version this device last saw — 0 rows back means another admin saved first, which `openConflict` surfaces as the root component's `cloudConflict` modal (Reload theirs / Overwrite with mine / Download my copy as JSON backup) instead of silently overwriting. Explicit full-replace actions (first-ever seed, Import Backup, Demo Sandbox "start fresh", Version History Restore) go through `sbSaveStateExplicit` instead — it loads the row's real current version first (never assumes "no row yet" from a stale local flag), seeds via `sbSeedState` (`Prefer: resolution=ignore-duplicates` — a concurrent seed from another device is detected as 0 rows back, never silently clobbered by `merge-duplicates`) only when truly absent, then falls through to a versioned PATCH either way. A `null` result from any of these means a concurrent write won the race: `saveCloudNow`/Demo "start fresh" (both in the root component, with access to the live conflict modal) call `openConflict`; Import/Restore (SettingsTab, no sensible "overwrite with mine" against a one-shot file/historical document) abort with an actionable "reload and try again" toast instead.
- **`dbReady` gates all cloud writes and stays false if mount-time load fails** — a device that never read the cloud must not overwrite it. A `row == null` result is AMBIGUOUS now, not just "empty cloud": PostgREST returns the same empty result whether the row never existed OR RLS silently filtered a non-admin/expired-session caller out. The mount effect resolves this via `sbIsAdmin()` (an `is_admin()` RPC call, unaffected by `res_state`'s own RLS) before trusting an empty result as "safe to seed" — don't remove that check, it's what keeps a blocked caller from seeding/overwriting a row it was never shown. `cloudBaselineRef` is now `{values, version}`, not a bare array — every read site must destructure `.values`/`.version`, not treat it as the array directly. Debounced (1.5s) save vs `cloudBaselineRef`; `flushPendingCloudSave()` awaits pending timer AND in-flight save; `saveCloudNow` no-ops while `cloudConflict` is up (checked via a ref, not state, so an already-scheduled debounce timer's stale closure still sees it).
- Settings → Version History: `sbFetchHistory` lists metadata only (`id`/`version`/`saved_by`/`saved_at`, last 50, no `data`, no `size` — a per-row size would need a DB-side computed column/view that doesn't exist yet) + `sbProfileEmails` (uuid→email, reachable because `profiles_admin_select_all` lets an admin read every profile). Preview/Restore lazily fetch ONE row's full `data` by id (`sbFetchHistoryData`) only when the admin actually opens that version — never all 50 up front. Preview uses `src/lib/stateDiff.js`'s `diffState(current, historicalSnapshot)` — pure, unit-tested, block/resident/schedule-cell counts only (a summary, not a field diff). Restore goes through `sbSaveStateExplicit` + the same cloud-op-first-then-reload path as `importData` (including `flushPendingCloudSave()` first, same as `deleteDemo`), refused in demo mode the same way.
- **Playgrounds** (2026-10-15, replaces the old single shared demo sandbox): per-admin disposable copies, one `res_state` row each, id `pg_<ownerUid>_<rand>` — `src/lib/playgrounds.js` has the pure id/guard/diff logic, unit tested there (`npm test` can't exercise cloud paths; see its tests for coverage). `physKey()` still rewrites `res_` → `res_demo_`, but only ONE physical slot exists at a time, for whichever playground is active — `res_demo_mode` holds that playground's row id (or legacy `'true'` = old shared demo, never auto-entered again, only offered once in the manager as "Old shared demo" to Resume-as-new-playground or Delete). `activeRowId` in the root component resolves that id; `assertWriteTargetRowId` guards every write path (`saveCloudNow`, import/clear/restore, promote) against targeting the wrong kind of row. Local-only (no Supabase) supports exactly ONE playground at a time (`res_pg_local_meta` device-local key). Promote ("Use this schedule for real…") is cloud-only (needs Version History's undo safety), typed-confirm, merges only the matched block's `schedule`+`lockedCells` into the real doc via a versioned PATCH — never roster/settings/rules. Detail in archive.

### Solver R9 (original wording)
- **R9 (2026-09-27) pipeline: local FIRST, always → solver POLISHES (warm-started) → `pickEngineResult` arbitrates.** `generateViaSolverOrLocal` runs `generateScheduleBest` before ever calling the solver, sends that schedule to the solver as `buildSolverPayload`'s optional `hint` (soft `AddHint`, never a hard pin like `locked[]`), and only ships the solver's result if it STRICTLY beats the already-computed local result — a tie or any solver failure keeps local, with no second wasted local run. Solver-side: staged (lexicographic) objective mirroring `betterQuality`'s own (errorCount, blockingWarnCount, qualityVector) ladder is now the default (`config.objectiveMode: 'staged'`); the old single weighted-sum solve is still available (`'weighted'`) for comparison. Full tier-mapping table, gaps, and search-tuning notes: `solver-service/docs/PAYLOAD_SCHEMA.md`'s dated R9 section.

### Scheduling/data-model (original wording)
- **Max 6 consecutive work days** (`MAX_CONSECUTIVE_WORK_DAYS`): counts CLINICAL SHIFTS ONLY (chief decision 2026-10-15, supersedes the earlier "GR weekday/JC presenting date also counts" ruling) — `isStreakWorkDay` is just assigned shift (incl. `prevBlockTailSchedules`); a shift-less GR weekday or JC date no longer extends a run. Shared by validator, generator, picker; solver's `workday_limits.py` mirrors it via an always-empty `obligations` payload field (mechanism kept, unused).
- **Rest between shifts** (ACGME 6.17.a.2, always hard): measured strictly from the earlier shift's own end — Grand Rounds never pushes it (chief decision 2026-10-15, supersedes the GR-end-adjustment ruling). GR's own hours toward the 60h/72h weekly caps DO still vary by what was worked the day before: 2h after an eve shift (10:00–GR_END_H), 2h after a night shift ending that morning (GR_START_H–10:00), 4h otherwise — see `lib/acgmeHours.js`'s `grWindowFor`/`grHoursOn`.
- **`availableRanges` is UNCLAMPED** (2026-10-14): `buildOffServiceResidentsForBlock` (Master Matrix import) stores an off-service resident's REAL ER rotation window, not clamped to the block being imported — clamping was a real bug that silently defeated `offServiceWindowStatus`'s straddle math on every import. `isAvailableOnDate` is always called with in-block dates only, so a wider range never leaks availability out-of-block. `OffServiceStraddleBadge` (+ pure `src/lib/offServiceWindow.js`) shows a resident whose window crosses a block edge at all 3 `offServiceWindowStatus` call sites — see `imports-exports` skill for detail.
