## CP-SAT solver service (optional second engine)
`solver-service/` — Python/FastAPI OR-Tools; contract in `solver-service/docs/PAYLOAD_SCHEMA.md`. Optional: `VITE_SOLVER_URL` unset → `SOLVER_ENABLED` false, app unchanged. Chief kill switch `appSettings.useSolverService` read as `!== false`. **The app resolves ALL policy into the payload; the solver only solves.**
- **R9 (2026-09-27): CP-SAT is a POLISHER, not a from-scratch competitor.** `generateViaSolverOrLocal` runs `generateScheduleBest` FIRST, always — the solver is warm-started from that schedule (`buildSolverPayload`'s optional `hint`, soft `AddHint`, never a hard pin) and must STRICTLY beat the already-computed local result (`pickEngineResult`, ties go local) to be shipped; any solver failure returns the local result directly. Solver-side default is now a STAGED (lexicographic) objective mirroring the JS `betterQuality` ladder (`errorCount` → `blockingWarnCount` → `qualityVector`) instead of one flat weighted sum — `config.objectiveMode: 'weighted'` reverts to the old single-shot solve. `num_workers` now defaults to `os.cpu_count()` (was hardcoded 8). Full tier-mapping table, the multi-worker native-crash finding (`repair_hint` + a repeated solve on the same model aborts the process — never combine them), and known gaps: `docs/PAYLOAD_SCHEMA.md`'s dated R9 section.
- **R9 follow-up, "pin to hint" (2026-09-27, `solver/model/hint_pin.py`):** before the staged solve, `evaluate_hint` fixes every `x` var to the hint's value on a CLONE of the model (never the real one, see the native-crash note above) and, if feasible under this payload's hard constraints, hard-pins `targetDeficitCore`/`postNightRest`/`coverageMin` (the 3 components JS's `betterQuality` ladder sees; deliberately NOT `overstaffCoverage`, which JS never scores; pinning it made 3/4 `engineHeadToHead` fixtures worse) at the hint's achieved values as hard `<=`, so the polisher can only match or beat the hint on those. `report.hintPinning` (`{applied, hintFeasible, pinned}`) rides along on every solve result. Day→next-day-evening is ALLOWED (user decision); only eve→next-day-day is hard (an earlier solver over-forbade day→eve and made the hint look infeasible; resolved 2026-09-27, see `docs/PAYLOAD_SCHEMA.md`'s R9 section "RESOLVED 2026-09-27").
- **Multi-hint portfolio (2026-10-31):** optional payload `alternateHints` (list of hint-shaped lists, lenient parse, cap 4, ignored without `hint`); portfolio run `i` warm-starts from `([hint]+alternateHints)[i % len]` (run 0 = primary), `report.portfolio.perRun[i].hintSource`. Client fills it from `generateScheduleBest(...).alternates` (same-tier distinct runner-ups, non-enumerable). `pickEngineResult` unchanged. See `docs/PAYLOAD_SCHEMA.md` last section.
- Seams in the big file: `buildSolverPayload()` (same args shape as `generateSchedule`, plus optional `hint`), `mapSolverResult()` (back to `{schedule, report}`), `generateViaSolverOrLocal()` — the ONLY solver-vs-local decision point, returns the already-computed local result on any solver failure (no second local run). `src/lib/solverClient.js` is the fetch wrapper (long timeout, solves legitimately run tens of seconds).
- **Night-run fragmentation solver term (2026-10-16, `objective.py`'s `_add_night_fragment_term`, rule 36b):** `isolatedNight` only penalized a truly isolated single night, so the solver had no incentive to merge two legal 2-6-night runs (measured on the real block: 120s polish cut isolated singles 21→17 but left 28/28 two-segment residents unchanged). The term mirrors `scheduleQuality.js`'s `nightShapePenalty` avoidable(2.3)/forced(2) split at the same x50 integer scale (`config/default_weights.json`'s `nightFragment.avoidableCost:115`/`forcedCost:100`). See `docs/PAYLOAD_SCHEMA.md`'s "Night-stint contiguity gap closed".

- **Auth + rate limiting on `/solve` (2026-10-14, `api/auth.py` + `api/ratelimit.py` + `api/limits.py`):** the deployed service had only `SOLVER_CORS_ORIGINS` (browser-only gate, useless against a direct caller). `SOLVER_AUTH_MODE` env (`off` default, `supabase`) gates a FastAPI dependency on `/solve` only; **`/health` stays open** (Fly's health check has no token). `off` keeps local `uvicorn`, `pytest`, and `cli.py` unauthenticated.
  - `supabase` mode requires `Authorization: Bearer <access_token>`, the Supabase session JWT the browser already holds via `supabaseClient.js`/`supabase.auth.getSession()`. A shared secret baked into the bundle would be pointless (readable from the JS); the session token is the only per-user credential.
  - Verifies signature + `exp` + `aud == 'authenticated'` + `role == 'authenticated'` + (when `SUPABASE_URL` is set) `iss == "${SUPABASE_URL}/auth/v1"`. Both Supabase signing schemes: asymmetric (current default) via JWKS at `${SUPABASE_URL}/auth/v1/.well-known/jwks.json` (`api/auth.py`'s `_JwksCache` — refetches only on an unknown `kid` or past its 10-minute TTL, never per-request), and legacy HS256 via `SUPABASE_JWT_SECRET` if set. Any failure (missing header, bad signature, expired, wrong aud/role/iss, unreachable JWKS) collapses to a flat 401 — never distinguishes which, and the raw token is never logged or put in an exception message.
  - **JWKS amplification guard**: a token with a random never-valid `kid` used to force a synchronous JWKS fetch (3s timeout) per request. `_JwksCache` now throttles fetch *attempts* (not just successes) to once per 60s globally, behind a lock; an unknown `kid` seen again inside that window 401s with zero network calls.
  - **Preauth rate limit, separate from the main bucket**: `enforce_preauth_ip_limit` (`SOLVER_PREAUTH_RATE_PER_MIN` default 30, `SOLVER_PREAUTH_RATE_BURST` default 10) is `/solve`'s FIRST dependency, running before `require_auth`; the per-subject bucket can't help against bad tokens since it only knows the subject after expensive verification. Coarse and IP-only on purpose (blunts flooding/amplification, not the real per-caller cap).
  - Rate limit: in-memory token bucket (`SOLVER_RATE_PER_MIN` default 6, `SOLVER_RATE_BURST` default 3), keyed by JWT `sub` in `supabase` mode or client IP in `off` mode (`enforce_rate_limit` runs `require_auth` first, so a rejected token never consumes a bucket slot). 429 + `Retry-After`. IP is read from the `Fly-Client-IP` header first (Fly sets/overwrites this on every request reaching the app — trustworthy), falling back to `request.client.host`; `X-Forwarded-For` is NEVER read (client-controlled, Fly doesn't scrub it). Idle buckets (no request in 10 min) are swept opportunistically (at most once/minute) so one-off keys don't grow the table forever. **Per-process** — Fly can run >1 machine for this service, so the effective cap under multiple machines is `SOLVER_RATE_PER_MIN × machine count`, not a hard global ceiling; a shared store (Redis) would be needed for that.
  - Body size cap: `SOLVER_MAX_BODY_BYTES` (default 5 MiB), enforced at the ASGI layer (`api/limits.py`'s `MaxBodySizeMiddleware`) ahead of Pydantic parsing, and against real streamed bytes (not just a trusted `Content-Length` header). **Must stay the innermost of the two app-level middlewares** — `app.add_middleware` prepends, so CORS is added SECOND (last) in `api/main.py` to end up outermost; otherwise a 413/401/429 raised before CORSMiddleware gets a chance never carries an `Access-Control-Allow-Origin` header, and a browser caller can't read the actual status/body, only a generic CORS failure.
  - **Names-in-payload check (for this same task): resident display names never reach the solver.** `buildSolverPayload` (`src/ResidentScheduler.jsx`) emits only `r.id` (a `uuid()`-generated opaque id) plus `cohort`/`target`/booleans/caps — no `firstName`/`lastName`. `solver/io/payload.py`'s `ResidentModel` has no name field either. The client (`mapSolverResult`) re-attaches display names locally by id after the solve comes back.
  - Client wiring is DONE: `ScheduleGrid`'s solver calls in `src/ResidentScheduler.jsx` (grep `getAccessTokenBounded`) send the Supabase session JWT when `!usingLocal && AUTH_ENABLED` (cloud target only; "This computer" never gets a token). Keep `supabase` mode consistent with that: a client that stops sending the token 401s every cloud call.
- **Background jobs ("Long solve", 2026-10-16 prototype, `api/jobs.py`): POST /jobs, GET /jobs/{id}, DELETE /jobs/{id}.** Same request shape as `/solve`, same auth (`require_auth`)/body-limit (`MaxBodySizeMiddleware` wraps every route) posture on submit, same `enforce_rate_limit` bucket as `/solve` on POST specifically — GET/DELETE deliberately do NOT share that bucket (a client polling every ~10-20s for up to 30 min would blow through `SOLVER_RATE_PER_MIN`'s default-6 budget almost immediately; they still go through the coarse `enforce_preauth_ip_limit`). One job runs at a time per process (`num_workers` already saturates every core) — a second concurrent submit gets 409. Jobs are **in-memory only**, swept 2h after finishing.
  - **Fly reality check (read before changing `fly.toml`): `auto_stop_machines=true` + `min_machines_running=0` means a job's machine can be stopped out from under it.** Fly stops a machine after no inbound traffic; an in-memory job is just gone. The client (`src/lib/solverJobs.js`) polling `GET /jobs/{id}` every ~10-20s is what holds the machine up via Fly's traffic-based autostop, not a deliberate keep-alive, and does nothing once polling stops (laptop sleeps, tab closes). A poll landing after a restart gets a plain 404 (new machine's `_jobs` never had the id); `pollSolveJob`/`cancelSolveJob` surface that as `{lost: true}`, and the UI's job client (ScheduleGrid's long-solve pill) must treat it as "optimizer stopped before finishing, run it again", never hang.
  - **Not fixed on purpose, a cost/ops decision for the repo owner:** (1) `auto_stop_machines = "off"` (or `min_machines_running = 1`) in `fly.toml` keeps the machine up, trading Fly compute cost (it scales to zero when idle, the reason `auto_stop_machines` was `true`; see that setting's comment in `fly.toml`) for job durability; or (2) an external keep-alive (scheduled ping to `/health` every few minutes while a job is outstanding). Either needs the owner's sign-off; a rare (2-3/month) admin-opt-in feature may not justify an always-on machine. For now a lost job is "run it again" and the UI says so.
  - **Cancellation mechanics (`solver/solve.py`'s `begin_stoppable_run`/`end_stoppable_run`):** a per-thread registry that every CpSolver `_configure_solver` creates is appended to IF the calling thread opted in via `begin_stoppable_run()` (sync `/solve` never does: zero-cost no-op). `DELETE /jobs/{id}` calls `.stop_search()` on every registered solver for up to 2s (OR-Tools' documented thread-safe API); a cancel landing between two of `_solve_staged`'s (up to 4) stage solves still stops the NEXT solver almost immediately (registered right before its own `.solve()`). `solve(payload, cancel_event=...)` also skips `run_pass2`'s second full solve when the event is set and pass 1 returned "INFEASIBLE" only because it was stopped (UNKNOWN); without that a cancelled job would start a whole second solve. Known gap: `hint_pin.py`'s `evaluate_hint` makes its own short-lived (<=30s) CpSolver outside the registry, so a cancel during that pre-check isn't interrupted (acceptable, always fast).
  - Client: `src/lib/solverJobs.js` (`submitSolveJob`/`pollSolveJob`/`cancelSolveJob`) builds on `solverClient.js`'s own `getSolverUrl()` base-URL resolution rather than duplicating it. App-side UI: ScheduleGrid's "Long Solve…" button (next to Generate/Deep Solve) + a non-blocking progress pill, persisted via the device-local `res_long_solve_job` key (NOT `LS_BACKUP_KEYS`/`syncBindings` — see this repo's root CLAUDE.md on device-local keys) so a pending job survives a reload. "Review in a playground" runs the job's result through the same `pickEngineResult` semantics as `generateViaSolverOrLocal` (ties/non-improvements say so and go nowhere) and, only on a strict win, creates a brand-new playground (via `promoteBlockSchedule`, the same merge helper "Use this schedule for real" already uses in the opposite direction) with the matched block's schedule replaced — never the real workspace.

- **Seed portfolio (2026-10-18, `config.portfolio`, `solver/solve.py`'s `_solve_portfolio`):** int 1..8, absent = auto, OFF since 2026-11-11 (`AUTO_PORTFOLIO_MIN_WORKERS = None`, so K=1; K=1×16 beat K=2 7W/2L on realScale at 120+300 s, see PERF_NOTES). Set to 12 restores the 2026-10-30 rule (K=2 when the effective worker count >= 12, else 1; `report.portfolio.auto=true`; explicit value incl. 1 always wins; `resolve_portfolio_k`), explicit 1 (= today's single `_solve_single`, no report key). K>1 runs K full solves (seed `randomSeed+i`) concurrently in threads inside the same process / Modal `solve_fn`, workers split `max(1, W // min(K,W))` per run, each with the full `maxTimeSeconds` (K>W -> batches, each run gets `maxTimeSeconds / batches` so wall time stays ~ budget). Failed runs show `status:"ERROR"` + `error` in `perRun`. Winner = lexicographic min of `SolveResult.tiers` (errors, blocking, coverage, rest-after-coverage, quality), ties to lowest index; `report.portfolio = {k, winnerIndex, perRun:[{seed,status,tiers,wallSeconds}]}`. Cancel: `_PortfolioStopper` in the caller's stoppable list stops every run. Trade: fewer workers per run, so it can lose to K=1 when parallelism matters; measure on the real block before making it a client default. Detail: `docs/PAYLOAD_SCHEMA.md` last section.
