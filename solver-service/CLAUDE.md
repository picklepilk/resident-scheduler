## CP-SAT solver service (optional second engine)
`solver-service/` — Python/FastAPI OR-Tools; contract in `solver-service/docs/PAYLOAD_SCHEMA.md`. Optional: `VITE_SOLVER_URL` unset → `SOLVER_ENABLED` false, app unchanged. Chief kill switch `appSettings.useSolverService` read as `!== false`. **The app resolves ALL policy into the payload; the solver only solves.**
- **R9 (2026-09-27): CP-SAT is a POLISHER, not a from-scratch competitor.** `generateViaSolverOrLocal` runs `generateScheduleBest` FIRST, always — the solver is warm-started from that schedule (`buildSolverPayload`'s optional `hint`, soft `AddHint`, never a hard pin) and must STRICTLY beat the already-computed local result (`pickEngineResult`, ties go local) to be shipped; any solver failure returns the local result directly. Solver-side default is now a STAGED (lexicographic) objective mirroring the JS `betterQuality` ladder (`errorCount` → `blockingWarnCount` → `qualityVector`) instead of one flat weighted sum — `config.objectiveMode: 'weighted'` reverts to the old single-shot solve. `num_workers` now defaults to `os.cpu_count()` (was hardcoded 8). Full tier-mapping table, the multi-worker native-crash finding (`repair_hint` + a repeated solve on the same model aborts the process — never combine them), and known gaps: `docs/PAYLOAD_SCHEMA.md`'s dated R9 section.
- **R9 follow-up, "pin to hint" (2026-09-27, `solver/model/hint_pin.py`):** before the staged solve runs, `evaluate_hint` fixes every `x` var to the hint's own value on a CLONE of the model (never the real one — see the native-crash note above) and, if that's feasible under this payload's hard constraints, hard-pins `targetDeficitCore`/`postNightRest`/`coverageMin` (the 3 components JS's `betterQuality` ladder can actually see — deliberately NOT `overstaffCoverage`, which JS never scores; an earlier version pinned it too and made 3/4 `engineHeadToHead` fixtures worse) at the hint's achieved values as hard `<=` constraints, so the polisher can only match or beat the hint on those, never trade one for another. `report.hintPinning` (`{applied, hintFeasible, pinned}`) rides along on every solve result. An earlier note here said the hint was judged INFEASIBLE on every `engineHeadToHead` fixture and blamed the JS generator for not enforcing day→next-day-evening as hard; that diagnosis was backwards and is RESOLVED 2026-09-27 — the solver was over-forbidding day→eve, which is ALLOWED (user decision); only eve→next-day-day is hard. See `docs/PAYLOAD_SCHEMA.md`'s R9 section ("RESOLVED 2026-09-27").
- Seams in the big file: `buildSolverPayload()` (same args shape as `generateSchedule`, plus optional `hint`), `mapSolverResult()` (back to `{schedule, report}`), `generateViaSolverOrLocal()` — the ONLY solver-vs-local decision point, returns the already-computed local result on any solver failure (no second local run). `src/lib/solverClient.js` is the fetch wrapper (long timeout, solves legitimately run tens of seconds).
- **Night-run fragmentation now has a solver term (2026-10-16, `objective.py`'s `_add_night_fragment_term`, rule 36b)** — closes a previously-documented gap (`docs/PAYLOAD_SCHEMA.md`'s "Night-stint contiguity gap closed"). Before this, `isolatedNight` only penalized a truly isolated single night; the solver had zero incentive to merge two already-legal 2-6-night runs into one (measured on the real block: 120s polish cut isolated singles 21→17 but left 28/28 two-segment residents completely unchanged). New term mirrors `scheduleQuality.js`'s `nightShapePenalty` avoidable(2.3)/forced(2) fragmentation split exactly, at the same x50 integer weight scale (`config/default_weights.json`'s `nightFragment.avoidableCost:115`/`forcedCost:100`).

- **Auth + rate limiting on `/solve` (2026-10-14, `api/auth.py` + `api/ratelimit.py` + `api/limits.py`):** the deployed service previously had only `SOLVER_CORS_ORIGINS` (commit 625a9c9) — a browser-only gate, useless against a non-browser caller hitting the Fly URL directly. `SOLVER_AUTH_MODE` env (`off` default, `supabase`) gates a FastAPI dependency on `/solve` only — **`/health` stays open**, Fly's health check has no token to send. `off` keeps local `uvicorn`, `pytest`, and `cli.py` unauthenticated exactly as before this existed.
  - `supabase` mode requires `Authorization: Bearer <access_token>` — the Supabase session's own JWT, same one the browser app already holds via `supabaseClient.js`/`supabase.auth.getSession()`. A shared secret baked into the bundle would be pointless (any caller can read it out of the JS); the Supabase-issued session token is the only thing that's actually per-user and can't be lifted from the bundle.
  - Verifies signature + `exp` + `aud == 'authenticated'` + `role == 'authenticated'` + (when `SUPABASE_URL` is set) `iss == "${SUPABASE_URL}/auth/v1"`. Both Supabase signing schemes: asymmetric (current default) via JWKS at `${SUPABASE_URL}/auth/v1/.well-known/jwks.json` (`api/auth.py`'s `_JwksCache` — refetches only on an unknown `kid` or past its 10-minute TTL, never per-request), and legacy HS256 via `SUPABASE_JWT_SECRET` if set. Any failure (missing header, bad signature, expired, wrong aud/role/iss, unreachable JWKS) collapses to a flat 401 — never distinguishes which, and the raw token is never logged or put in an exception message.
  - **JWKS amplification guard (post-review fix, same day)**: a token with a random never-valid `kid` used to force a synchronous JWKS fetch (3s timeout) on every request. `_JwksCache` now throttles fetch *attempts* (not just successes) to at most once per 60s globally, behind a lock (no thundering herd); an unknown `kid` seen again inside that window 401s with zero network calls.
  - **Preauth rate limit, separate from the main bucket**: `enforce_preauth_ip_limit` (`SOLVER_PREAUTH_RATE_PER_MIN` default 30, `SOLVER_PREAUTH_RATE_BURST` default 10) is wired as `/solve`'s FIRST dependency, running before `require_auth` is even invoked — without it, the per-subject bucket below can't help, since it only knows the subject *after* a token has already been verified (expensively, for a bad asymmetric token). Coarse and IP-only on purpose; it exists to blunt flooding/amplification, not to be the real per-caller cap.
  - Rate limit: in-memory token bucket (`SOLVER_RATE_PER_MIN` default 6, `SOLVER_RATE_BURST` default 3), keyed by JWT `sub` in `supabase` mode or client IP in `off` mode (`enforce_rate_limit` runs `require_auth` first, so a rejected token never consumes a bucket slot). 429 + `Retry-After`. IP is read from the `Fly-Client-IP` header first (Fly sets/overwrites this on every request reaching the app — trustworthy), falling back to `request.client.host`; `X-Forwarded-For` is NEVER read (client-controlled, Fly doesn't scrub it). Idle buckets (no request in 10 min) are swept opportunistically (at most once/minute) so one-off keys don't grow the table forever. **Per-process** — Fly can run >1 machine for this service, so the effective cap under multiple machines is `SOLVER_RATE_PER_MIN × machine count`, not a hard global ceiling; a shared store (Redis) would be needed for that.
  - Body size cap: `SOLVER_MAX_BODY_BYTES` (default 5 MiB), enforced at the ASGI layer (`api/limits.py`'s `MaxBodySizeMiddleware`) ahead of Pydantic parsing, and against real streamed bytes (not just a trusted `Content-Length` header). **Must stay the innermost of the two app-level middlewares** — `app.add_middleware` prepends, so CORS is added SECOND (last) in `api/main.py` to end up outermost; otherwise a 413/401/429 raised before CORSMiddleware gets a chance never carries an `Access-Control-Allow-Origin` header, and a browser caller can't read the actual status/body, only a generic CORS failure.
  - **Names-in-payload check (for this same task): resident display names never reach the solver.** `buildSolverPayload` (`src/ResidentScheduler.jsx`) emits only `r.id` (a `uuid()`-generated opaque id) plus `cohort`/`target`/booleans/caps — no `firstName`/`lastName`. `solver/io/payload.py`'s `ResidentModel` has no name field either. The client (`mapSolverResult`) re-attaches display names locally by id after the solve comes back.
  - Client wiring is DONE: `ScheduleGrid`'s solver calls (`src/ResidentScheduler.jsx` ~15135/15211/15231/16026) send the Supabase session JWT via `getAccessTokenBounded()` when `!usingLocal && AUTH_ENABLED` (cloud target only; "This computer" never gets a token). Keep `supabase` mode consistent with that — a client that stops sending the token will 401 every cloud call.
- **Background jobs ("Long solve", 2026-10-16 prototype, `api/jobs.py`): POST /jobs, GET /jobs/{id}, DELETE /jobs/{id}.** Same request shape as `/solve`, same auth (`require_auth`)/body-limit (`MaxBodySizeMiddleware` wraps every route) posture on submit, same `enforce_rate_limit` bucket as `/solve` on POST specifically — GET/DELETE deliberately do NOT share that bucket (a client polling every ~10-20s for up to 30 min would blow through `SOLVER_RATE_PER_MIN`'s default-6 budget almost immediately; they still go through the coarse `enforce_preauth_ip_limit`). One job runs at a time per process (`num_workers` already saturates every core) — a second concurrent submit gets 409. Jobs are **in-memory only**, swept 2h after finishing.
  - **Fly reality check (read before changing `fly.toml`): `auto_stop_machines=true` + `min_machines_running=0` means a job's machine can be stopped out from under it.** Fly's proxy stops a machine once it sees no inbound traffic for a while; an in-memory job has no way to survive that — it's just gone, state and all. The client (`src/lib/solverJobs.js`) polling `GET /jobs/{id}` every ~10-20s while its tab is open is *also* what's holding the machine up via Fly's own traffic-based autostart/autostop, not a deliberate keep-alive mechanism — there's no guarantee it's enough under load, and it does nothing at all once polling stops (laptop sleeps, tab closes, browser crashes). A poll that lands after the machine already restarted gets a plain 404 (the new machine's in-memory `_jobs` dict never had this id) — `pollSolveJob`/`cancelSolveJob` surface that as `{lost: true}`, and the UI's job client (ScheduleGrid's long-solve pill) must treat it as "optimizer stopped before finishing, run it again", never hang waiting on a job that can't come back.
  - **Not fixed here on purpose — a cost/ops decision for the repo owner, not this prototype:** two real mitigations exist and neither was applied: (1) `auto_stop_machines = "off"` (or `min_machines_running = 1`) on this service in `fly.toml` — keeps the machine up permanently, trading Fly compute cost (this service currently scales to zero when idle, which is the whole reason `auto_stop_machines` was set `true` in the first place — see that setting's own existing comment in `fly.toml`) for job durability; or (2) a lightweight external keep-alive (e.g. a scheduled ping to `/health` every few minutes) while any job is outstanding, which keeps the machine's own autostop timer from firing without a developer having to pay for 24/7 `min_machines_running=1`. Either needs the repo owner's sign-off on the cost tradeoff — a rare (2-3/month), admin-opt-in feature doesn't obviously justify paying for an always-on machine. For now: a lost job is just "run it again," and the UI says so.
  - **Cancellation mechanics (`solver/solve.py`'s `begin_stoppable_run`/`end_stoppable_run`):** a per-thread registry that every CpSolver instance `_configure_solver` creates gets appended to, IF the calling thread opted in via `begin_stoppable_run()` first (the synchronous `/solve` path never does, so it's a zero-cost no-op there). `DELETE /jobs/{id}` calls `.stop_search()` on every currently-registered solver for up to 2s (OR-Tools' own documented safe-from-another-thread, no-op-if-already-done API) — this can race the brief gap between two of `_solve_staged`'s (up to 4) per-stage solves, in which case the NEXT solver (registered right before its own `.solve()` call) still gets stopped almost immediately rather than that stage running to completion. `solve(payload, cancel_event=...)` also skips `run_pass2`'s second full solve when the event is already set and pass 1 came back "INFEASIBLE" only because it was stopped early (status UNKNOWN) — without that check, a cancelled job would silently kick off a whole second solve instead of actually stopping. One known gap: `hint_pin.py`'s `evaluate_hint` creates its own short-lived (<=30s-capped) CpSolver outside this registry, so a cancel landing exactly during that narrow pre-check isn't interrupted — acceptable for a prototype since that solve is always fast by construction.
  - Client: `src/lib/solverJobs.js` (`submitSolveJob`/`pollSolveJob`/`cancelSolveJob`) builds on `solverClient.js`'s own `getSolverUrl()` base-URL resolution rather than duplicating it. App-side UI: ScheduleGrid's "Long Solve…" button (next to Generate/Deep Solve) + a non-blocking progress pill, persisted via the device-local `res_long_solve_job` key (NOT `LS_BACKUP_KEYS`/`syncBindings` — see this repo's root CLAUDE.md on device-local keys) so a pending job survives a reload. "Review in a playground" runs the job's result through the same `pickEngineResult` semantics as `generateViaSolverOrLocal` (ties/non-improvements say so and go nowhere) and, only on a strict win, creates a brand-new playground (via `promoteBlockSchedule`, the same merge helper "Use this schedule for real" already uses in the opposite direction) with the matched block's schedule replaced — never the real workspace.
